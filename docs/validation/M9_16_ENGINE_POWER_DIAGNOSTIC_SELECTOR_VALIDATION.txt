3. Implemented causal boundary

Exactly one powertrain.engineTorqueMultiplier owns the current engine calibration.
Default is 1.0. It scales the sampled immutable engine torque curve before the
existing throttle, gear, final-drive, efficiency, shift-drive and redline factors.
The setter changes only that validated positive finite scalar. RPM, shift state,
wheel Omega and body motion are never overwritten to apply the setting.

Browser choices: 1.0 / 1.5 / 2.0 / 3.0 / 4.0.
Keyboard: K, one cycle per non-repeated keydown.
Touch/mouse: ENG xN cycling button after the three tire buttons.
HUD: ENG [K] xN alongside the existing tire readout.

All three browser composition roots use the same getter-based control adapter.
Manual and automatic/route recovery preserve the scalar while resetting dynamics.
Safe-spawn vehicle replacement copies it to the new powertrain instance.
Rivals and ordinary constructors remain at 1.0; a full page/course reload resets
it to 1.0. No persistent storage or second browser selection state is introduced.

4. New executable checks

- Exact domain, default, K mapping, formatting and deterministic wraparound.
- All nine profile torque curves remain immutable. At prescribed identical wheel
  speed and state, the independent piecewise torque oracle reproduces 1x delivery;
  all five multipliers scale sampled and delivered torque while leaving RPM,
  gear, shift timer and shift direction equal.
- Zero throttle, shift-drive cutoff and top-gear redline cutoff still give zero
  output for every selectable multiplier.
- Setter mutates only the scalar; another vehicle is unaffected. Non-positive,
  NaN and infinite values are rejected before mutation.
- Manual and explicit wrong-course recovery retain 4x, clear dynamic output and
  actuator state, and do not alter tire calibration.
- Shared tire/engine DOM fixture preserves the original three tire controls;
  engine click/K act on the current vehicle even after replacement. Tire actions
  do not change engine calibration; engine actions do not change tire calibration.
- A 2x versus 1x ordinary vehicle step produces greater delivered drive torque
  and forward speed through the existing wheel/tire path, with tires and brakes
  unchanged.
- All nine profiles remain finite at 4x in one-second, 60 Hz flat-surface probes
  starting at 25 m/s, steering=0.25 and full throttle, for G2/P24/S2 and G3/P24/S3.
  These are bounded finite-response probes, not sustained-drift acceptance tests.
- All three composition roots mount/route the adapter and retain calibration on
  replacement. Source checks retain lower-layer independence. CSS keeps the
  shared group at three tire columns plus a full-width engine row in landscape,
  or four columns in portrait.

5. Scope and limitations

No tire law, tire G/P/S choices or defaults, steering law, actuator rates, brake
capacity, immutable vehicle profile, shift strategy, redline rule, camera,
renderer, route topology, workflow or input gesture is changed.

M9.15 browser S still ranges from 1.00 to 2.00. G2/S2 is an available no-drop
browser point. The G3/S3 regression is constructed through the existing numeric
tire-calibration API and is not an unrequested browser-domain expansion.

The tests establish correct scaling, isolation and lifecycle. They do not prove
pleasant drift, adequate sustained power, long-run stability at every combination,
or physical-device touch/layout quality. UI verification here uses DOM fixtures,
source checks and the retained browser regressions, not an actual phone playtest.
Local cloning/execution was not used as evidence; executable evidence is the
complete GitHub Actions exact-head run above.
